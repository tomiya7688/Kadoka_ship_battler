# Kadoka ship battler

船内で弾を運び、砲台を動かし、仲間と役割分担しながら敵船と戦う船バトルゲームです。

## Development

- Engine: **Unity 6.3 LTS**
- Language: **C#**
- Editor used for local verification: `6000.3.24f1`

Unity Hub からリポジトリのルートディレクトリを開いてください。

## Playable prototype

`Assets/KadokaShipBattler/Scenes/BattlePrototype.unity` を開いて Play を押してください。

- WASD / 矢印: 移動
- E: 近くの弾を拾う / 砲台へ装填 / 装填済みの砲台を発射
- Space: 通常攻撃（敵船員 / 敵コア）
- Tab: 次の生存している味方へ操作対象を切り替える
- R: 再開始

黄色・オレンジ色が弾、灰色が砲台、紫がコアです。弾を4発当てて敵船体HPを0にすると中央の橋を通れます。敵船へ渡ってコアを破壊すると勝利します。船体HP0だけでは勝敗は決まりません。敵は見えている弾を拾って砲台へ戻り、装填できると最短10秒間隔で砲撃します。自船体が破壊されると橋から乗り込み、視界内の船員やコアを攻撃します。

両陣営はそれぞれ25枠の弾デッキを持ちます。シーン開始時に各船の8地点へランダムに出現し、その後は2秒ごとに空いている地点へ最大1発を補充します。初期の弾種は通常弾15発・重い弾10発です。画面にはデッキの待機数を表示します。

現在は仮の図形・味方5人／敵5人によるプロトタイプです。白いマーカーと画面のControl欄が操作対象を示します。切替時に位置・向き・所持弾を保持し、元の船員は直ちに弾運搬AIへ戻ります。HPが0になった船員は行動・操作できなくなり、操作中なら生存している味方へ切り替わります。船員全滅だけでは勝敗は決まりません。

味方のAIは現在位置と現在向きから前方120度・距離6以内の見える弾を探し、運搬→装填→発射を実行します。弾が見えない時は向きを変えて探します。砲台の位置は既知情報です。敵には視界内の敵を通常攻撃する簡単な防衛AIがあり、先頭の行動可能な砲撃担当が砲撃・乗り込みを行います。運搬と乗り込みは部屋・ドアの経路探索を使います。味方は更新型Utility AIで運搬・装填・砲撃・防衛を比較します。

### AIの視界

全船員に `VisionSensor` を付け、弾・船員・コアを前方扇状の視界から観測します。既定の `ViewAngle` は120度、`ViewDistance` は6です。センサーのInspectorまたは `Configure(angle, distance)` で変更できます。距離は対象の中心までで、角度・距離の境界を含めます。自分自身は観測対象にしません。

壁・閉じたドアの `Collider2D` と同じGameObject、またはその親へ `VisionBlocker` を追加すると、視線が遮られます。通常の船員・弾のコライダーは視線を遮りません。ドアが開いた時はBlockerまたはコライダーを無効にしてください。トリガーの壁にも対応します。トリガー検出の全体設定が無効な環境では、同期クエリ中だけ有効にし、終了・例外時に元へ戻します。永続的な物理設定は変更しません。

観測にはその時点のID・位置・HP・弾の重量と威力を保存し、視界外へ移動・遮蔽・取得・死亡・無効化・破棄された対象を現在のキャッシュから除外します。以前の観測データは値を保持し、隠れた対象の現在状態を読む参照を持ちません。対象へ作用する直前にも視界を再確認し、古い観測からの取得・攻撃を拒否します。

味方の弾運搬、敵の補給、防衛攻撃はセンサーの観測を使います。自船砲台の位置は既知マップ情報として扱います。敵の乗り込みも部屋・ドア・橋の経路探索を使い、攻撃対象は現在見える相手に限定します。現在の敵の目的地はプロトタイプ用の固定コア地点です。敵船内の探索・戦術判断はIssue #11で接続します。壁による遮蔽は実際のCollider2Dを使ったPlayModeテストで検証しています。

Play中に船員を選択し、SceneビューのGizmosを有効にすると、選択船員の視野と観測対象への線を確認できます。味方の評価関数は現在の観測値と自船情報から候補を採点します。物理クエリのAPIは [UnityのOverlapCircleリファレンス](https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/physics2d/overlapcircle) を参照してください。

### 編成とキャラクターデータ

[`PrototypeCrew.json`](Assets/KadokaShipBattler/Data/PrototypeCrew.json) に共通のキャラクター定義と両陣営の5枠を保存しています。`characters` に定義を追加し、`player.slots` / `enemy.slots` のIDを変更すると次のシーン開始時に反映されます。各陣営の先頭枠がリーダーです。5枠でない編成、未定義・重複定義のID、範囲外の能力値は開始前に拒否します。同じキャラクターを複数枠へ配置することはできます。

| 船員 | HP | 移動速度 | 通常攻撃 | 攻撃力 | 射程 | 弾硬度 | 飛行 / すり抜け |
|---|---:|---:|---|---:|---:|---:|---|
| Leader | 100 | 4 | 接触 | 25 | 0.9 | 2 | false / false |
| Gunner | 70 | 2.8 | 遠距離 | 40 | 2.5 | 1 | false / false |
| Carrier | 90 | 3.5 | なし | 0 | 0 | 2 | false / false |
| Scout | 60 | 5 | 接触 | 15 | 0.9 | 1 | true / true |
| Defender | 180 | 2 | 接触 | 50 | 0.9 | 5 | false / false |

接触攻撃は射程内、遠距離攻撃は現在向きの前方120度・射程内の最も近い敵へ即時にダメージを与えます。どちらも壁越しの攻撃を拒否します。弾が飛ぶ処理と硬度判定はIssue #16で接続します。飛行・すり抜けの値は経路条件と移動判定に反映します。修理能力は使用できません。

`attackMode` は0=なし・1=接触・2=遠距離です。`capabilities` はCombat=1、CarryAmmo=2、OperateCannon=4、BoardEnemyShip=16、Support=32の合計値です。修理用の8は指定できません。`combatSkill` / `carrySkill` は0〜10の適性です。

### 重量と保持数

| 船員 | 許容合計重量 | 最大保持数 |
|---|---:|---:|
| Leader | 5 | 2 |
| Gunner | 3 | 1 |
| Carrier | 9 | 3 |
| Scout | 3 | 1 |
| Defender | 0 | 0 |

黄色の弾は重量2、オレンジ色の弾は重量3です。どちらもダメージ25です。追加時は個数と合計重量の両方を判定します。Leaderは「2+2」「2+3」を持てますが「3+3」は持てません。満杯・重量超過で拾えなかった弾はその場に残ります。

Eで砲台へ装填する時は、先に拾った弾を1発だけ渡します。残りの弾と重量は保持します。Tabで操作を外しても複数の所持弾は失われず、復帰したAIも同じ運搬判定を使って順番に装填・発射します。AIは運べない弾を探索候補から除外します。

`CharacterDefinition` の `CarryCapacity` / `MaxCarryCount` と `AmmoDefinition` の `Weight` が定義データです。実行中に上限を下げた場合、すでに持っている弾は保持し、追加取得を制限します。重量は取得時の値を保持して集計します。

### 25枠の弾デッキと循環

[`PrototypeAmmo.json`](Assets/KadokaShipBattler/Data/PrototypeAmmo.json) の `ammo` が弾種定義、`player.slots` / `enemy.slots` が各陣営の25枠です。同じIDを複数枠に入れられます。弾種には威力・重量・硬さを設定でき、通常弾の硬さは2、重い弾は4です。レア度はありません。出現時は待機している実際の枠から均等にランダム選択します。

1枠に対応する弾は、出現→運搬→装填→着弾まで同じ個体として追跡します。地面・船員の所持品・砲台にある弾も使用中として数えるため、同時存在数はデッキ内の実個数を超えません。着弾すると待機へ戻り、再び出現候補になります。現在の砲撃は即時着弾です。飛行・弾同士の衝突・撃ち落としはIssue #16の段階で接続します。

地面の弾は60秒で消滅・返却します。運搬・装填中にはこの時間制限を適用しません。船員死亡・所持品や砲台の破棄・シーン終了でも返却し、同じ個体を二重取得・二重返却できないようにしています。キャラクターの許容重量・個数を超えて拾えなかった弾は、その場に残ります。

`layouts` は船種ごとの出現地点です。船の中心からの相対座標を指定し、敵側は左右を反転して配置します。`playerLayout` / `enemyLayout` で使用する船種を選びます。現在はstandardとcargoの2種類を使用し、船外の出現地点は拒否します。同じ船種IDの部屋マップを使用し、出現地点が部屋の内部または通行可能なドアにあることも確認します。敵の定型砲撃も自船デッキの実個体を消費し、弾が無い場合には発射しません。

### 船内の部屋と経路

`PrototypeNavigation.json` にstandard・cargoの部屋矩形とドア接続を保存しています。座標は船中心からの相対値で、敵側は左右を反転します。船種は弾データの `playerLayout` / `enemyLayout` と共通です。砲台は相対(2,0)、侵入口は相対(3,0)で共通です。

- `rooms`: IDとminX/minY/maxX/maxY。部屋の内部は重ねられません。
- `doors`: 接続するfrom/to、共有境界上のpoint、通路幅width、isOpen。
- `requiredAbilities`: 0=通常、1=飛行、2=すり抜け、3=両方。
- `allowPhaseWhenClosed`: すり抜け能力で閉じたドアを通過できるか。通常の壁はすり抜けできません。

通常の船員は中央のドアとコア室のハッチを使います。Scoutは上側の飛行通路と下側の閉じたすり抜けドアも使えます。飛行でも閉じた通常ドアや船体未破壊の橋は通れません。すり抜け能力でも壁越しの視界は得られません。

`BattleNavigation.TryFindPath` が距離を比較して経路を選び、`NavigationAgent.MoveTo` が指定地点へ移動します。`MoveToRoom("Player/core", deltaTime)` は部屋中央へ移動します。AIは目的地を決め、経路探索と移動は共通の移動系へ渡します。自船内の移動、橋を通る敵船への移動、帰還を同じ処理で扱います。船体破壊の条件は陣営別に判定します。

`SetDoorOpen("Player/main-door", false)` でドアを閉じると経路を再探索し、壁の描画・視界遮蔽も直ちに反映します。経路がなければ停止し、開閉・能力・船体状態・目的地が変われば再探索します。移動区間全体を検査するため、大きな移動量でも壁や海を飛び越えません。操作切替・死亡・戦闘終了で移動を解除します。

現在の船員は点として通行判定します。船員同士の押し合い、体格に応じた通路幅、敵船の探索知識、戦術的な目的地選択は含みません。

### 味方の更新型評価関数

チーム方針と船員ごとの個人方針を変更する際は、Pキーまたは画面右上の`AI policies [P]`を押してください。能力が足りない選択肢は理由付きの無効ボタンになります。AIは次の判断時に新しい設定を反映します。操作方法、緊急補正、検証範囲は[チーム方針と個人方針](Docs/AiPolicies.md)を確認してください。

味方の `UtilityAiAgent` は毎回の観測から待機・弾運搬・装填・砲撃・船内防衛の候補を作り、点数が最も高い候補を選びます。`CrewAmmoAiController` が選ばれた行動を実行し、共通の `NavigationAgent` へ目的地を渡します。操作を外れた瞬間にも現在位置・向きから再評価します。

| 評価する要素 | 使用する情報 |
|---|---|
| 距離 | 使用可能な部屋・ドアを通る経路の長さ。到達できない候補は除外 |
| 危険度 | 現在見えている敵船員と候補地点との距離 |
| 適性 | 自分のcombatSkill・carrySkill、行動能力、攻撃の可否 |
| 戦況 | 自分のHP、自船の船体HP、所持弾、自船砲台の装填状態、自船デッキ待機数 |
| 弾種 | 現在観測した弾の威力・重量。実際に運べる弾だけを候補にする |
| 学習値 | その船員の行動結果から更新した重み |

最終点数は「基礎点 × 学習重み × 方針重み」です。標準設定では所持弾の装填と装填済み砲台の発射を優先し、見えている自船の侵入者への防衛も比較します。同点は行動番号・対象IDで決めます。修理や実行処理が未接続の行動は候補にしません。

取得・装填・砲撃・攻撃の成功は正、作用や移動の失敗は負の結果として学習値へ反映します。重みは0.25〜4に制限し、結果に対して徐々に近づけます。`Learning.SetWeight(action, weight)` で調整でき、`Learning.RecordOutcome(action, reward, learningRate)` は-1〜1の結果と0〜1の学習率を受け取ります。戦闘終了後にも更新できます。

`JsonUtility.ToJson(agent.Learning.Export())` で重みをJSONへ取り出し、次の船員の `Learning.Import(JsonUtility.FromJson<UtilityLearningData>(json))` へ渡せます。自動保存は未接続で、Rによる再開始では初期重みへ戻ります。操作切替や判断解除では同じ船員の学習値を保持します。

選択された `Decision` と各候補の `Scores` は値のスナップショットです。対象の現在位置・HPを読む参照を持ちません。実行直前には視界・取得条件・攻撃条件を再確認します。敵の隠れた所持品・行動・デッキ・プレイヤー入力・未来の出現は評価に渡しません。

EditorまたはDevelopment Buildでは、味方のUtilityAiAgentのInspectorでShow Debugを有効にすると選択行動と上位3候補の「基礎点×学習重み×方針重み」を表示します。Gizmosでは目的地への線を表示します。通常のリリースビルドにはこの表示処理を含めません。

チーム・個人方針の設定UIはIssue #6、担当の予約と共有はIssue #7、敵5人の戦術判断と観測共有はIssue #11で接続します。今回の学習は、行動結果による重み補正です。

## CI and verification

通常のGitHub Actionsは `.NET 10` で本番の `BattleModel.cs`、`CrewControlState.cs`、`CrewDefinitions.cs`、`AmmoDeckModel.cs`、`VisionModel.cs`、`NavigationModel.cs`、`UtilityModel.cs` を直接コンパイルし、実際の編成・弾デッキ・部屋マップJSONを読み込んで戦闘・操作切替・重量と保持数・5人編成とHP・デッキ循環・視界・経路探索・AI評価と学習の315項目を検査します。Unityのメタデータ・シーン登録・JSONのシーン参照も確認します。

```powershell
dotnet run --project Tools/CI/GameplayChecks.csproj --configuration Release
```

UnityのTest RunnerのPlayModeテストは91件です。実シーンの戦闘・勝敗・描画に加えて、操作切替、状態保持、AI復帰と運搬・砲撃、船員別の移動・攻撃、重量と保持数の上限、複数弾の順次装填、両陣営5人の生成、HP・死亡時の操作切替、データ追加、弾デッキの出現・装填・着弾・時間切れ・破棄時の返却、25枠の使い切り、扇状視界・壁とドア・観測消失・AIの視界制限、部屋指定の移動、壁の通過拒否、飛行・すり抜け、ドア開閉時の再探索、船間の往復、壁越しの取得・攻撃の拒否、適性・学習値による判断変更、学習付きの実際の運搬・防衛、判断解除、視界外・到達不能な候補の除外も検査します。

GitHub上のUnity PlayModeジョブには別途ライセンス設定が必要です。変数 `RUN_UNITY_TESTS=true` と、GameCIに適合する `UNITY_LICENSE` または `UNITY_EMAIL` / `UNITY_PASSWORD` / `UNITY_SERIAL` をsecretsへ設定してください。ローカルUnityのライセンスはGitHubへ自動転送されません。未設定時はUnityジョブがskippedになり、通常の戦闘ロジックCIは実行されます。

## Architecture

ゲーム定義と実行ロジックを分離します。

- `ScriptableObject`: キャラクター、弾、AI方針などの定義データ
- `MonoBehaviour`: 船、船員、戦闘中の実体
- Utility AI: 行動候補を評価値で比較して選択
- Team policy / Character policy: Utility AI の評価値へ補正を加える
- Capability: キャラクターが実行可能な行動そのものを制限

キャラクター固有モーションや見た目は判断ロジックから分離し、同じ行動でもキャラクターごとに表現を差し替えられる構造を目指します。

## Initial gameplay target

1. プレイヤーと敵の船を1隻ずつ配置する
2. プレイヤーが船内を移動する
3. 弾を拾って砲台へ運ぶ
4. 砲台へ装填して発射する
5. 敵船にダメージを与える
6. 味方4人・敵5人をAIで動かす
7. AI方針・弾デッキ・キャラクター適性によって行動傾向を変える

## AI principles

- 味方AIは更新型評価関数を持ち、弾デッキや戦闘傾向へ徐々に適応する
- チーム方針とキャラクター方針は別々に設定する
- キャラクターごとに選択可能な方針が異なる
- 戦闘が強いキャラクターの多くは運搬を不得意とするなど、役割間にトレードオフを持たせる
- 敵AIは賢くするが、未観測の隠し情報を直接読むチートAIにはしない
